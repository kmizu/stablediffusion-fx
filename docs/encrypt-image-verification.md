## Upstream and compatibility

The behavior reference is `viyiviyi/sd-encrypt-image`, commit `3a44d3c264632aa90442bdc50e42af0770289bfd`, AGPL-3.0. Its normal image-save wrapper scrambles PNG pixels using a password, records an `Encrypt` marker and can record `EncryptPwdSha`; its independent batch operations transform images between folders. Read compatibility covers `pixel_shuffle`, `pixel_shuffle_2` and `pixel_shuffle_3`; new compatibility files use version 3. The independent implementations are behavior-based; the isolated upstream core was used to generate comparison fixtures, not as the application engine. Core reference SHA-256: `31b06b74b6cf8ebe7d294469eebe588cd767e4675cbcdb00106e19fb5bd61065`; wrapper SHA-256: `69af9299ea92b8769804d793ca7fd9e095f055518af7c27f827f5c7c090a66b0`. `scripts/third_party.py` records the reference and licence. Notice collection succeeded for 159 projects in `outputs/encrypt-notices-retry.log` (exit 0); verify the notices against the final source during acceptance.

This is deterministic pixel permutation, **not authenticated or secure encryption**. Metadata remains readable. Without a verifier in a legacy file, password correctness is unknown, not confirmed; the batch restore requires explicit opt-in for such files. Verification where a marker exists does not turn this format into authenticated encryption.

## Implemented paths

* The Python and JVM codecs read the three formats and write v3. The desktop session holds a redacted in-memory password snapshot; jobs capture their own snapshot, including the permission for readable video, so subsequent changes do not change queued jobs. The password travels in a worker envelope rather than generation parameters. It is not a claim of secure memory erasure.
* Generated PNGs and grids use the job snapshot; image views and supported script reads resolve marked PNGs with the session or job snapshot. Generation image inputs and supported tool inputs are decoded to scoped temporary files where the worker requires a path. Session changes invalidate or refresh relevant views. MainWindow now mounts Session and Batch conversion controls.
* Batch conversion uses different source and destination folders, retains source files, avoids intentional overwrites, and reports existing, skipped, unverified and failed files. Conversion output is PNG; JPEG/WebP metadata and original file bytes cannot be assumed preserved.
* Intermediate and animation PNGs support scrambling. Videos and GIFs are readable exports and require the session's explicit plaintext-video permission. Protected ffmpeg recipes prompt for the password at execution and decode temporary frames. VAE tools and recovery distinguish scrambled RGB/RGBA images from readable latent data and recovery tensors. Temporal Lab and WD batch have protected paths; their precise observed coverage is in the logs below.
* Custom Code is arbitrary Python: it may write readable files outside the app's control. Its controls disclose this; a protected job logs a warning. It is not sandboxed by the image session.

## Exposure and limits

* PNG text, EXIF and other preserved metadata are readable. EXIF can contain an embedded thumbnail with recognizable original pixels. Batch conversion of PNG can carry such metadata into scrambled output. Scrambling is not a confidentiality boundary for metadata.
* Worker images, decoded inputs, clipboard/drop image inputs and video encoding frames can exist as readable temporary files. Normal cleanup is not secure deletion, and a crash can leave remnants. Clipboard copying deliberately exposes decoded pixels to the system clipboard. Displayed previews are readable on screen.
* GIF/video and consented latent outputs are readable; exact VAE recovery tensors remain readable. Captions and other metadata may also disclose content. Custom Code can write arbitrary readable data. MCP runs separately from the desktop session. The session does not make unrelated files or past ordinary outputs protected.
* Legacy files without a password verifier may decode to incorrect pixels without a detectable wrong password. Some older format and PNG modes have different codec constraints; preserve original files during conversion. Batch processing stops after the current image on request, rather than rolling back previously completed outputs.
* 16-bit LA PNG compatibility is unsupported. Format conversion does not preserve arbitrary metadata or original encoded bytes; protected recipe launchers record installation paths and may need regeneration after moving the installation. SVD real-model acceptance and complete cancellation/recovery coverage remain outstanding.
