# Batch interrogator internal protocol boundary

Status: partial internal preparation. The JSON-lines server routes prepare and execute requests, but production service is not configured, no capability is advertised, and there is no UI feature or full extension acceptance. Without a trusted service, requests return unsupported. The existing v3 candidate is one local WD-family model; CLIP, Deepbooru and other WD/CLIP EXT models remain unavailable. Backend availability is established by explicit reviewed assets and an actual worker environment, never by a self-declared public request.

Freeze the checkpoint token, selected ordered backend, exact internal `FileSnapshot` identities, generation parameters, output destination and composer options before queueing. Public inputs must later be scanned and verified by worker-owned code; callers must not manufacture trusted snapshots, asset pins, registries or provider objects through JSON. At execution, require the same loaded checkpoint token before any backend work and before/after each generation. The owned runner provides staging and exact-job cancellation; changes to the model abort the whole batch and prevent publication. Engine queue serialization is a required external invariant and these checks do not make concurrent pipeline mutation safe.

The eventual protocol must expose per-item effective prompts, selected model identity/options and terminal failure/cleanup; serialized queue and `EngineSupervisor` need targeted pre-start/in-flight/commit cancellation, protection retry, timeout settlement, stale callback suppression and no-clobber output. Native UI must present partial capability and offline asset requirements, preserve disabled still generation, and never claim missing backend parity. These worker/Scala/UI integrations, PNG metadata persistence, resource hard limits, full parity, real SD generation and release acceptance remain open. Do not add a public feature flag before these are reviewed.

The internal worker handshake accepts only the fixed WD v3 provider and pinned candidate, configured by trusted worker setup rather than JSON. Preparation stores at most eight worker-owned snapshots for five minutes. The unguessable token is a bearer secret, not an authenticated identity; `owner_id` is a routing label and comparison guard, not authentication. Execute consumes the token on an attempt after its initial interruption check: a cancellation before consumption leaves it usable, while cancellation or any failure after consumption requires a new preparation. The registry table is copied on service creation, but same-process trusted code can still mutate the provider; no defense against hostile in-process code is claimed. Production service registration, public capability and a user-facing workflow remain absent.
