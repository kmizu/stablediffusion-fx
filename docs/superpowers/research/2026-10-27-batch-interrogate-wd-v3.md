# Batch interrogator: local WD v3 feasibility

Read-only inventory and source research, 2026-10-27. No model or package download, ONNX session, inference, GPU use, or network-based execution was performed. This is not evidence that the batch feature works, that WD EXT parity is complete, or that a model can be redistributed.

## Actual local files and provenance

The existing Hugging Face cache has a `SmilingWolf/wd-vit-tagger-v3` snapshot at revision `7f6b584d0bd3f55c4531f14ba3d4761b2bccdc0f`; `refs/main` points to it. The snapshot's `model.onnx` and `selected_tags.csv` are symbolic links to local cache blobs. Read-only SHA-256 over the blob bytes gave:

| selected_tags.csv | 308,468 | `298633d94d0031d2081c0893f29c82eab7f0df00b08483ba8f29d1e979441217` |

The model blob name equals the calculated model SHA-256; the CSV blob's cache name is different from its calculated SHA-256. The snapshot and filenames are evidence of a locally cached candidate, not independent authentication of either byte sequence against the publisher. No model download was used to compare them. CSV parsing gives 10,861 rows: 8,106 category 0, 2,751 category 4 and four category 9.

The pinned [model card](https://huggingface.co/SmilingWolf/wd-vit-tagger-v3/blob/7f6b584d0bd3f55c4531f14ba3d4761b2bccdc0f/README.md) identifies ONNX, states Apache-2.0 in its metadata, names ratings/general/character outputs and requires ONNX Runtime >= 1.17. The repository's [model](https://huggingface.co/SmilingWolf/wd-vit-tagger-v3/blob/7f6b584d0bd3f55c4531f14ba3d4761b2bccdc0f/model.onnx) and [tags](https://huggingface.co/SmilingWolf/wd-vit-tagger-v3/blob/7f6b584d0bd3f55c4531f14ba3d4761b2bccdc0f/selected_tags.csv) pages identify the same revision and nominal file sizes. The card's license metadata is useful provenance, not a complete audit of licensing, bundled notices, dataset rights or authorization to redistribute binary weights. The Python requirements declare `onnxruntime==1.23.2`; a `onnxruntime-1.23.2.dist-info` directory exists in the shared parent virtual environment. This does not establish that the application's shipped environment imports it or that the runtime loads this model.

## Behavior and differences

The author's [reference ONNX app](https://huggingface.co/spaces/SmilingWolf/wd-tagger/blob/87f2e2e9165e9b2c41209d57a4022ae7d01cf91c/app.py) reads tag categories 9/0/4, composites transparent input over white, square-pads with white, bicubic-resizes, and presents a float32 BGR batch to the ONNX session. It uses a strict `>` general-tag threshold and sorts by score; it treats ratings and characters separately and preserves listed underscore emoticons. This describes that particular app revision, not proof of the pinned batch extension's complete WD EXT behavior. Confirm the WD extension's actual ordering, rating formatting, character handling, threshold boundaries, underscore/escaping and model-specific options separately against its pinned source.

The existing `extras.wd14_tags` instead invokes `hf_hub_download` on cache misses, keeps its session/CSV in the shared `_caption_cache`, uses `>=` for general tags and does not expose ratings or character outputs. It discards alpha by converting to RGB before padding. The separate internal batch registry now retains RGBA for providers that explicitly request it; existing providers continue to receive RGB. WD v3 is a WD-family option, not the original native Deepbooru or CLIP; it must never be labeled as either.

The pinned [batch extension source](https://raw.githubusercontent.com/Alvi-alvarez/sd-Img2img-batch-interrogator/ed91cec663bcddd7ca5514264a61483c7d80f8d2/scripts/sd_tag_batch.py) converts each input to RGB before calling WD EXT, defaults to `wd-v1-4-moat-tagger.v2`, keeps tag scores strictly above its threshold, optionally replaces underscores except for named emoticons, and includes ratings at or above their threshold. It delegates label ordering and inference to whichever WD EXT is separately installed. The next paragraph describes one specifically pinned WD EXT revision, not necessarily the version used by every installation; full parity remains unverified. The internal v3 candidate instead preserves alpha and composites on white according to the referenced model-author example; this is an explicit preprocessing difference for transparent images. It uses CSV order provisionally and is not a substitute for the native Deepbooru/CLIP choices or proof of WD EXT parity.

The separately pinned WD extension at [e72d984bdbed832ba83e2a443238c3851b9088ae](https://raw.githubusercontent.com/picobyte/stable-diffusion-webui-wd14-tagger/e72d984bdbed832ba83e2a443238c3851b9088ae/tagger/interrogator.py) passes results in CSV order, uses its first four rows as ratings and the rest as tags, and calls its [image utilities](https://raw.githubusercontent.com/picobyte/stable-diffusion-webui-wd14-tagger/e72d984bdbed832ba83e2a443238c3851b9088ae/tagger/dbimutils.py): pad to at least target size and downscale with OpenCV `INTER_AREA`. The internal v3 path pads to image size then resizes using Pillow bicubic; both the padding behavior for small images and interpolation for downscaling can change pixels and scores. Exact comparison and parity are unverified. Rights for any copied or adapted portions of that separate extension and its dependencies remain unresolved; source similarity and citations do not themselves establish a grant.

The internal registered batch result records each successful item's effective prompt, selected provider model ID, model SHA-256 and tag CSV SHA-256, both thresholds, underscore/rating flags and preprocessing policy. The WD runtime verifies its fixed local candidate bytes; those hashes are not independently authenticated publisher hashes. The generic registry's provider provenance is self-reported and checking its values before and after a batch cannot prove that a provider or its assets were not replaced in between. This structured result is not embedded into the generated PNG; worker protocol, UI metadata and persistent PNG provenance remain unimplemented.

## Proposed offline connection and gates

1. Treat the existing local model and CSV as explicit user-selected assets. Bind the canonical regular blob bytes to an independently reviewed, immutable identity; the cache snapshot aliases are symlinks, so do not weaken the no-link guard merely to admit them. Define an explicit user-visible workflow for selecting/copying them into an owned private staging area without modifying source files. Enforce size and streaming digest on both, bind loading to verified staged bytes, and retain exact source path/revision/hash separately. Do not accept an arbitrary protocol-supplied trust manifest.
2. Before considering an ONNX model safe to load, establish the pinned model's input/output signature, external-data references and actual operator/resource requirements from independently reviewed metadata. Reject external data, custom libraries/operators, unknown model signatures and unbounded CSV sizes/schema; do not assume ONNX is safe merely because it is not pickle. Define limits before session creation, decoded input and output allocation. ONNX Runtime and native operator allocations are not covered by a Python file-size limit.
3. Construct a CPU-only ONNX Runtime session from the verified local model without calling `hf_hub_download`, transformers loading, or an implicit repository lookup. Keep session ownership per operation and release on success, error and cancellation; unload failure must be visible and occur before output publication. Interrupt checks can surround native calls but do not necessarily interrupt an active native ONNX invocation. Preserve alpha until the selected model's documented compositing step.
4. Validate image and output shapes, finite probabilities, row count, supported category values and cumulative text size. Implement the batch extension's exact WD thresholds, rating behavior, ordering and emoji escaping as a separate tested contract. Show the actual model identifier and user-selected options; default WD EXT model differs from this v3 candidate.
5. Only advertise the backend after offline-denial tests, safe-load review, faithful fake boundary fixtures and a small real local CPU inference validate this exact pair. Record source and hashes, input/output and cleanup evidence; verify real use through the owned Img2img batch. No such inference or end-to-end evidence exists in this research. CLIP, Deepbooru, other WD models and full extension parity remain open.
