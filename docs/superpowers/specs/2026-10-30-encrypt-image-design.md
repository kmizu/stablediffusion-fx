# Image encryption compatibility design (#48)

The upstream extension at `viyiviyi/sd-encrypt-image`, pinned at `3a44d3c264632aa90442bdc50e42af0770289bfd`, scrambles PNG pixels when a password is configured and unscrambles them on read. It supports legacy `pixel_shuffle`, `pixel_shuffle_2`, and `pixel_shuffle_3` inputs; new files use version 3. Its independent batch tools also transform directories. The metadata remains readable, the same password deterministically produces the same rearrangement for a given image size, and this permutation is not modern authenticated encryption. Compatibility must be labeled as scrambling, never presented as secure encryption. Wrong passwords can only be identified when the optional upstream verifier is present; files without it cannot authenticate a password.

The target is native opt-in save/read integration preserving generation, gallery/preview, transfer to img2img, metadata and ordinary files, plus non-destructive batch import/export. Do not persist or log passwords, do not overwrite source files, and do not silently fall back to plaintext if protection is enabled. Capture queued settings, avoid exposing plaintext temporary files in output directories, and clearly disclose plaintext previews, metadata and any other storage scope. Preserve original formats only where feasible; compatibility files are PNG. The integration design must inventory all image save/read routes before claiming complete coverage. Source-compatible scrambling and strong authenticated encryption solve different problems; implementing one does not prove the other. No strong-security promise will be made for this compatibility mode.

Source files and license may be studied and tested; project policy requires reimplementation from behavior, with AGPL notice. No parent reForge code is imported or launched. This design is provisional on concrete integration inspection; the open issue remains todo until all its requirements and actual SD1.5/SDXL, cancellation and package checks pass.
